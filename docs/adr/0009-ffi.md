# ADR-9: Calling C functions from scripts (the `ffi` library)

Status: Accepted

## Context

Many Lua C modules are thin wrappers that convert arguments and call one C function. An FFI lets a script bind the C function itself. It isn't memory-safe, but it is less code and less risk than a C module, which has the same reach plus its own C bugs.

## Decision

### Shape
- **`orbit-ffi`**, behind the `ffi` feature of `orbit-std`, off by default. Embedders that build with it call `orbit_std::install_ffi`; otherwise scripts don't get the library. `orbit-cli` turns the feature on and enables the library unless started with `--no-ffi`.
- **A library API, not syntax.** `ffi.open`, `lib:bind` / `ffi.bind`, `ffi.errno`, `ffi.buffer`, `ffi.string`, `ffi.get`, `ffi.set`, `ffi.offset` and `ffi.sizeof`, with types named by strings. Both languages use the same API; [`docs/design/ffi.md`](../design/ffi.md) is the reference.
- **A `std.` module, not a global.** Scripts reach it as `require "std.ffi"` in Lua and `use std::ffi;` in OrbitScript, as they reach `std.json` (ADR-12). It is not in OrbitScript's prelude, and `require` fails unless the host enables it.
- **libffi makes the calls**, through `libffi-sys`. By default libffi is built from bundled sources and linked statically (needs a C compiler, `sh` and `make`; only the C compiler on MSVC). The `ffi-system-libffi` feature links the system's shared libffi instead; Apple targets always use the system's.

### Calls
- Every 64-bit target libffi supports, with its default calling convention. Libraries load with `dlopen` on Unix and `LoadLibraryA` on Windows.
- Binding prepares libffi's call description (`ffi_cif`) once per distinct signature. Arguments may go on the stack, so there is no register limit.
- **FFI functions are natives with two data words**, the C address and the signature's index in the library's per-isolate state, so they take the direct native call path rather than the slower native-closure path. Natives are never freed, so bindings are interned per address and signature.
- C can't call back into the VM, so nothing runs in the VM during a C call and no collection can move a string the call is reading.
- Not covered yet: variadic functions, structs by value and callbacks. libffi supports all three, so each is library work.

### Containment
- **`unsafe`** is allowed only in `orbit-ffi/src/sys.rs`: `dlopen` and `dlsym`, calls through libffi, memory access through script-supplied addresses, and reading C strings (ADR-6).
- Once enabled, the process is only as memory-safe as the scripts' declarations and pointer use. That is why the library is off for embedders and has a CLI switch.
- **Buffers are the safe default.** `ffi.buffer` memory is owned by the script and bounds-checked on every access; raw pointers are not.
- **Scripts can't forge pointers.** Pointer arguments accept only light userdata, buffers and `nil`; `ffi.offset` is the only arithmetic.
- **Scripts can't redirect calls.** A function's address lives in its native's data, out of reach of `debug.setupvalue`.

## Alternatives rejected

- **Our own call trampolines** (exact function types per arity, plus one 6-integer, 8-double type for the rest). Faster per call and smaller, but they covered only System V x86_64 and AAPCS64, relied on a calling-convention detail Rust doesn't promise, and were hard to follow.
- **FFI functions as native closures.** Each call would pay the closure stub frame.

## Consequences

- Release `orbit` grows by about 55 KiB with bundled libffi, or 37 KiB with the system's (cloud x86_64).
- A call costs about 4x a fast-path Rust native, about the same as a call through the C module shim.
