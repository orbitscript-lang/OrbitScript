# ADR-9: Calling C functions from scripts (the `ffi` library)

Status: Proposed (2026-10-14). Tym asked for a production FFI on 2026-10-14: behind a Cargo feature, enabled by default in the CLI with a flag to turn it off, and without OrbitScript declaration syntax for now. Accepting this record also grants the `unsafe` exception below.

## Context

Many Lua C modules are thin wrappers that convert arguments and call one C function. Writing, building and shipping such a module for each library is the main reason people reach for C. An FFI lets a script bind the C function itself. It isn't memory-safe, but it is less code and less risk than a C module, which has the same reach plus its own C bugs.

The spike (`spike/ffi`, never merged; `planning/ffi/` in the project files) measured three things:

- Our own register trampolines are enough for the common signatures, so libffi isn't needed.
- An FFI call costs about what a Rust native does.
- The VM's native-closure call path costs 15-20 ns per call, so FFI functions must not be native closures.

The assessment in the same folder found that rewriting parts of the standard library over FFI would not save binary size, so this record does not cover that.

## Decision

### Shape
- **A new crate, `orbit-ffi`,** behind the **`ffi`** Cargo feature of `orbit`, which is off by default.
  - **Embedders** who build with it must also call `Lua::enable_ffi()`; otherwise scripts don't get the library.
  - **`orbit-cli`** turns the feature on by default and enables the library unless started with `--no-ffi`.
- **A library API, not syntax.**
  - The calls are `ffi.open`, `lib:bind` / `ffi.bind`, `ffi.errno`, `ffi.buffer`, `ffi.string`, `ffi.get`, `ffi.set`, `ffi.offset` and `ffi.sizeof`, with types named by strings. Both front ends use the same API; `docs/design/ffi.md` is the reference.
  - `ffi` is added to OrbitScript's prelude, so `.orb` code can use it without `extern ffi;`. It is absent at run time unless the host enables it.
  - OrbitScript `extern fn` declarations are a later, separate decision. They would lower to `bind` calls, and the attribute form waits for the language-wide attribute design.
- **No new dependencies.** Calls go through trampolines in `orbit-ffi/src/sys.rs`, not libffi.

### Calls
- **Supported targets:** 64-bit Unix on x86_64 and aarch64, where the System V and AAPCS64 conventions pass integer-class and floating-point arguments in separate registers.
- **Call shapes:**
  - All-integer signatures with an integer result call through an exact function type of their arity.
  - Up to three `double`s call through an exact `double` type.
  - Everything else calls through one type with six integer and eight `double` parameters. The callee reads the registers its signature names.
- **Not covered:**
  - Variadic functions, structs by value, stack arguments, and callbacks.
  - Windows x64, which assigns registers by position; `ffi.supported` is false there and `ffi.open` raises.
- **Calling through a non-exact function type is not something Rust's rules promise,** even though it matches the platform convention. It is confined to `call_mixed` and the `float` case. A C or assembly trampoline (the C module shim already builds C) is the fallback if that ever matters.

### The VM side
- **`Vm::register_native_with_data(name, f, [u64; 2])` and `NativeCtx::native_data()`.** A native can carry two words that it reads on every call. FFI functions are such natives, holding an address and a packed signature, so they take the direct native call path.
- **Natives are never freed,** so `orbit-ffi` interns bindings per address and signature. Each `Native` entry grows by 16 bytes.
- **C can't call back into the VM,** so nothing runs in the VM during a C call and no GC can move a string the call is reading.

### Containment
- **`unsafe` (ADR-6 exception):** `orbit-ffi` denies `unsafe_code` and allows it only in `src/sys.rs`. That file covers `dlopen` and `dlsym`, the trampolines, reading and writing memory through script-supplied addresses, and reading C strings. Every other crate keeps `forbid`.
- **Once enabled, the process is only as memory-safe as the scripts' declarations and pointer use.** A wrong signature, a dangling pointer, or a C function keeping a pointer into a `cstr` copy can corrupt memory. That is why the library is off for embedders and has a CLI switch.
- **Buffers are the safe default for memory.** `ffi.buffer` memory is owned by the script and bounds-checked on every `get`, `set`, `string` and `offset`; raw pointers are never checked.
- **Scripts can't forge pointers from integers.** Pointer arguments accept only light userdata, buffers and `nil`. `ffi.offset` is the only arithmetic.
- **Scripts can't redirect calls.** The address a function calls lives in its native's data, out of reach of `debug.setupvalue` and of scripts.

## Consequences
- **Size:** release `orbit` grows by about 35 KiB with the feature (1,909,488 to 1,945,744 bytes, cloud x86_64, no PGO).
- **Speed:** an FFI call costs about 2x a fast-path Rust native and about 0.4x a call through the C module shim. Cloud x86_64 numbers are in `docs/design/ffi.md`.
- **C modules benefit from the same VM change.** Moving C functions from native closures to natives with data would speed up `orbit-capi` too; that is separate work.
- **Later work:**
  - Windows x64 call shapes.
  - Callbacks, which need a re-entrant native call like the C API's `NativeCtx::call` plus generated thunks.
  - Struct helpers.
  - OrbitScript `extern fn` sugar.
- **PGO:** the committed profile doesn't cover the new code; the next retrain should include an FFI workload.
