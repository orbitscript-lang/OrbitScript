# ADR-9: Calling C functions from scripts (the `ffi` library)

Status: Accepted (Tym, 2026-10-18; proposed 2026-10-14, revised 2026-10-15). Tym asked for a production FFI on 2026-10-14: behind a Cargo feature, enabled by default in the CLI with a flag to turn it off, and without OrbitScript declaration syntax for now. On 2026-10-15 he chose libffi over our own call trampolines, with how it is linked left to a crate option. Accepting this record also granted the `unsafe` exception below and the `libffi-sys` dependency.

## Context

Many Lua C modules are thin wrappers that convert arguments and call one C function. Writing, building and shipping such a module for each library is the main reason people reach for C. An FFI lets a script bind the C function itself. It isn't memory-safe, but it is less code and less risk than a C module, which has the same reach plus its own C bugs.

The spike (`spike/ffi`, never merged; `planning/ffi/` in the project files) measured two things that still hold:

- An FFI call through our own register trampolines cost about what a Rust native does.
- The VM's native-closure call path costs 15-20 ns per call, so FFI functions must not be native closures.

The first version of this record used those trampolines: exact function types per arity, and one 6-integer, 8-double function type for everything else. It was faster per call and smaller, but it covered only the System V x86_64 and AAPCS64 conventions, relied on a calling-convention trick Rust doesn't promise, and was hard to follow. Tym chose libffi on 2026-10-15 for readability and target coverage.

The assessment in the same folder found that rewriting parts of the standard library over FFI would not save binary size, so this record does not cover that.

## Decision

### Shape
- **A new crate, `orbit-ffi`,** behind the **`ffi`** Cargo feature of `orbit-std` (of `orbit` before ADR-11), which is off by default.
  - **Embedders** who build with it must also call `orbit_std::install_ffi` (feature `ffi` on `orbit-std`; it was `Lua::enable_ffi()` before ADR-11); otherwise scripts don't get the library.
  - **`orbit-cli`** turns the feature on by default and enables the library unless started with `--no-ffi`.
- **A library API, not syntax.**
  - The calls are `ffi.open`, `lib:bind` / `ffi.bind`, `ffi.errno`, `ffi.buffer`, `ffi.string`, `ffi.get`, `ffi.set`, `ffi.offset` and `ffi.sizeof`, with types named by strings. Both front ends use the same API; `docs/design/ffi.md` is the reference.
  - `ffi` is added to OrbitScript's prelude, so `.orb` code can use it without `extern ffi;`. It is absent at run time unless the host enables it.
  - OrbitScript `extern fn` declarations are a later, separate decision. They would lower to `bind` calls, and the attribute form waits for the language-wide attribute design.
- **libffi makes the calls,** through the `libffi-sys` crate (raw bindings, no other runtime dependencies).
  - By default `libffi-sys` builds libffi from its bundled sources and links it statically, so the binary has no new runtime dependency. Building needs a C compiler, `sh` and `make` (only the C compiler on MSVC).
  - The `system-libffi` feature of `orbit-ffi`, passed through as `ffi-system-libffi` on `orbit-std` and `orbit-cli`, links the system's shared libffi instead. MSVC targets always use the bundled copy.

### Calls
- **Targets:** every 64-bit target libffi supports with its default calling convention, loading libraries with `dlopen` on Unix and `LoadLibraryA` on Windows. Linux x86_64 is tested; macOS, Windows and aarch64 Linux are only checked to compile.
- **Binding** prepares libffi's call description (`ffi_cif`) once per distinct signature. Arguments may go on the stack, so there is no register limit.
- **Not covered yet:** variadic functions, structs by value, and callbacks. libffi supports all three, so each is library work rather than a new call mechanism.

### The VM side
- **Natives with data words.** A native can carry two words that it reads on every call (`Control::register_native` and `native_data` on `orbit::stack`; `Vm::register_native_with_data` before ADR-11). FFI functions are such natives, holding the C address and the index of their signature in the library's per-VM state, so they take the direct native call path.
- **Natives are never freed,** so `orbit-ffi` interns bindings per address and signature. Each `Native` entry grows by 16 bytes.
- **C can't call back into the VM,** so nothing runs in the VM during a C call and no GC can move a string the call is reading.

### Containment
- **`unsafe` (ADR-6 exception):** `orbit-ffi` denies `unsafe_code` and allows it only in `src/sys.rs`. That file covers `dlopen` and `dlsym`, the calls through libffi, reading and writing memory through script-supplied addresses, and reading C strings. Every other crate keeps `forbid`.
- **Once enabled, the process is only as memory-safe as the scripts' declarations and pointer use.** A wrong signature, a dangling pointer, or a C function keeping a pointer into a `cstr` copy can corrupt memory. That is why the library is off for embedders and has a CLI switch.
- **Buffers are the safe default for memory.** `ffi.buffer` memory is owned by the script and bounds-checked on every `get`, `set`, `string` and `offset`; raw pointers are never checked.
- **Scripts can't forge pointers from integers.** Pointer arguments accept only light userdata, buffers and `nil`. `ffi.offset` is the only arithmetic.
- **Scripts can't redirect calls.** The address a function calls lives in its native's data, out of reach of `debug.setupvalue` and of scripts.

## Consequences
- **Size:** release `orbit` grows by about 55 KiB with the feature and bundled libffi (1,909,488 to 1,965,320 bytes), or about 37 KiB when linking the system's libffi (cloud x86_64, no PGO). The trampolines were about 35 KiB.
- **Speed:** a call through libffi costs 20-35 ns more than through the trampolines did, about 4x a fast-path Rust native, and about the same as a call through the C module shim. libffi's own `ffi_call` takes about 40 ns for a 3-argument call from C on the same machine. Cloud x86_64 numbers are in `docs/design/ffi.md`.
- **C modules benefit from the same VM change.** Moving C functions from native closures to natives with data would speed up `orbit-capi` too; that is separate work.
- **Later work:**
  - Variadic functions (`ffi_prep_cif_var`).
  - Callbacks, through libffi closures plus a re-entrant call from a native into a script function.
  - Structs by value and struct helpers.
  - If call cost matters, a direct-call fast path for the simplest signatures could sit beside libffi.
  - OrbitScript `extern fn` sugar.
- **PGO:** the committed profile doesn't cover the new code; the next retrain should include an FFI workload.
